# CredentialAuthority — сервис выдачи удостоверений

Приложение предназначено для задания на ревью PR. Клиент создаёт заявку на
удостоверение, опрашивает её состояние и получает готовый JSON-документ.
Бизнес-правила и HTTP-контракт ниже являются требованиями к реализации.

## Границы исходной версии

- .NET 10, ASP.NET Core Web API, SQLite; один экземпляр приложения.
- Единственный заранее заданный издатель `Demo Authority`. Клиент не выбирает
  издателя и не может изменить его через API.
- Одноразовый `DatabaseInitializationWorker` подготавливает БД при старте.
- `IssuanceWorker` обходит ожидающие заявки каждые 10 секунд.
- Удостоверение — JSON, без криптографии, подписи и формата X.509.
- Авторизация, UI, управление издателями, отзыв, продление, удаление,
  пагинация и отдельный ключ идемпотентности не входят в исходную версию.
- Поддержка нескольких издателей — отдельная будущая доработка.

## Бизнес-правила

### BR-001. Имя владельца

Обязательная строка длиной 1–20 символов включительно. Первый символ —
латинская или русская буква. Допустимые символы:
`a-z`, `A-Z`, `а-я`, `А-Я`, `0-9`, `.`, `-`, `_`, `@`.
Буквы `ё` и `Ё`, пробелы, обратная косая черта и остальные символы запрещены.
Имя не обрезается и не исправляется автоматически.

### BR-002. Сравнение и представление имён

Регистр не учитывается: `Ivan` и `IVAN`, `Иван` и `иван` — один владелец.
Сравнение не зависит от региональных настроек процесса или БД. Похожие
латинские и русские буквы остаются разными символами.
В ответах сохраняется написание имени из принятой заявки.

### BR-003. Ограничение выдачи и повторная подача

У владельца может быть не более одного удостоверения за всё время.
Истечение удостоверения не разрешает новый выпуск.

| Существующие заявки владельца | Новая заявка |
| --- | --- |
| Нет | Разрешена |
| Только `Rejected` | Разрешена |
| Есть `Pending` | Запрещена |
| Есть `Issued` | Запрещена |

После `Rejected` создаётся новая заявка с новым ID. Старая заявка доступна
по прежнему ID и не изменяется. Число отклонённых попыток не ограничено.

### BR-004. Параллельные запросы

Ограничение BR-003 действует и при одновременных запросах, включая различия
только в регистре имени. Проверка и сохранение не должны допускать две
заявки `Pending` или два удостоверения одного владельца.

### BR-005. Срок при приёме заявки

`validUntil` — обязательная дата и время в ISO 8601 с явным часовым поясом:
`Z` или смещением. Например, `2030-12-31T23:59:59Z`.
При проверке заявки `validUntil` должно быть строго позже текущего времени
сервера. Некорректное значение, отсутствие часового пояса и уже наступивший
срок приводят к отказу в создании заявки.

### BR-006. Срок при выпуске

При выпуске обработчик повторно проверяет срок. Одно значение времени
используется для проверки и для `issuedAt`: если оно меньше `validUntil`,
выпуск разрешён; иначе заявка получает `Rejected` с причиной
`ValidityExpired`, удостоверение не создаётся.

### BR-007. Неизменяемость результата

В удостоверение переносятся имя владельца, издатель и `validUntil` заявки.
Срок не продлевается. Выпущенное удостоверение не изменяется и не удаляется.
Оно считается истёкшим при `текущее время >= validUntil`, но остаётся
доступно через API. Все даты в ответах возвращаются в UTC с суффиксом `Z`.

## HTTP API

JSON-поля используют camelCase. ID заявок и серийные номера — непустые UUID.
Издатель представлен строкой. Ошибки возвращаются в формате Problem Details.
Сначала проверяются формат и значения полей, затем — конфликт владельца.

### FR-001. Создать заявку

`POST /requests`, `Content-Type: application/json`.

```json
{
  "ownerName": "Ivan.Petrov",
  "validUntil": "2030-12-31T23:59:59Z"
}
```

Успех: `202 Accepted`, заявка сохранена в состоянии `Pending`.

```json
{
  "id": "a48a66bd-4400-4660-8703-f3b14034fc04"
}
```

Заголовок `Location`: `/requests/{id}`.

- `400 Bad Request`: некорректное тело, имя или срок; отсутствующие поля.
- `409 Conflict`: уже есть `Pending` или `Issued` для этого владельца.
- При отказе новая заявка не создаётся.

Издатель определяется сервером при создании и сохраняется вместе с заявкой.
Успешный ответ означает сохранение заявки, а не выпуск удостоверения.
К моменту последующего GET обработчик уже может завершить её обработку.

### FR-002. Получить карточку заявки

`GET /requests/{id}` → `200 OK`.

| Поле | Когда присутствует |
| --- | --- |
| `id` | Всегда |
| `status` | Всегда: `Pending`, `Issued` или `Rejected` |
| `ownerName` | Всегда |
| `issuer` | Всегда |
| `validUntil` | Всегда |
| `credentialUrl` | Только для `Issued` |
| `rejectionReason` | Только для `Rejected`; значение `ValidityExpired` |

Неприменимые поля отсутствуют, а не возвращаются с `null`.
`credentialUrl` — относительный URL `/credentials/{serialNumber}`.
Неизвестный или некорректный ID возвращает `404 Not Found`.

### FR-003. Обработать ожидающие заявки

Фоновый обработчик запускает обход каждые 10 секунд; первый обход —
через 10 секунд после запуска. Обходы не выполняются параллельно.
Если обработка занимает больше периода, следующий обход начинается после
завершения текущего без параллельной обработки пропущенных тактов.
Новые заявки могут попасть в следующий обход.

Допустимые переходы: `Pending → Issued`, `Pending → Rejected`.
Оба конечных состояния неизменяемы. Истечение уже выпущенного удостоверения
не меняет состояние заявки `Issued`.

### FR-004. Повтор после технического сбоя

Ошибка хранения или другая временная техническая ошибка не является
предметным отказом: заявка остаётся `Pending` для следующего обхода.
Ошибка журналируется с ID заявки; обработчик не выполняет бесконечный
немедленный повтор одной заявки и не прекращает обработку остальных.
При повторе срок проверяется заново. Остановка приложения не переводит
заявки в `Rejected`.

### FR-005. Согласованность и повторная обработка

Создание удостоверения и перевод заявки в `Issued` фиксируются атомарно.
Если GET показывает `Issued`, документ уже доступен по `credentialUrl`.
Повторная обработка не создаёт второй документ, не меняет серийный номер,
время выпуска и конечное состояние.

### FR-006. Состав удостоверения

| Поле | Содержание |
| --- | --- |
| `serialNumber` | Уникальный во всём приложении непустой UUID |
| `ownerName` | Имя из заявки с исходным написанием |
| `issuer` | Издатель из заявки |
| `issuedAt` | Время выпуска в UTC |
| `validUntil` | Окончание действия из заявки в UTC |

Серийный номер не обязан быть последовательным.

### FR-007. Получить удостоверение

`GET /credentials/{serialNumber}` → `200 OK` и JSON удостоверения.
Неизвестный или некорректный номер → `404 Not Found`.
Истёкшее удостоверение также возвращается с `200 OK`.

## Хранение и эксплуатация

- **NFR-001:** заявки и удостоверения сохраняются в SQLite между перезапусками.
- **NFR-002:** после перезапуска `Pending` обрабатываются обычным фоновым обходом.
- **NFR-003:** бизнес-проверки времени тестируются без ожидания реальных секунд.
- **C-001:** один экземпляр приложения и один фоновый обработчик.
- **C-002:** для запуска не требуются внешние сервисы и учётные записи.
- **C-003:** структура и дизайн реализации следуют [архитектуре](docs/architecture.md).

## Запуск и отладка в Rider после клонирования

1. Установите [.NET SDK 10](https://dotnet.microsoft.com/download/dotnet/10.0)
   и Rider с поддержкой .NET 10. Для первого восстановления пакетов нужен
   доступ к nuget.org.
2. Откройте `src/CredentialAuthority.sln` в Rider и дождитесь восстановления
   NuGet-пакетов.
3. Выберите launch-профиль `CredentialAuthority.Api` и нажмите **Run** или
   **Debug**. Профиль находится в
   [launchSettings.json](src/CredentialAuthority.Api/Properties/launchSettings.json).
4. Откройте [CredentialAuthority.Api.http](src/CredentialAuthority.Api/CredentialAuthority.Api.http)
   и запускайте запросы последовательно кнопками рядом с ними: создание,
   чтение заявки, получение удостоверения. Для чтения повторите запрос
   после ближайшего 10-секундного обхода.

[Rider автоматически импортирует launch-профили](https://www.jetbrains.com/help/rider/Running_LaunchSettings.html).
Если solution уже открывался и профиль не появился, нажмите правой кнопкой
на `Properties/launchSettings.json` и выберите **Generate Configurations**.
Для breakpoint подойдут `CreateRequestUseCase.Execute` и
`IssueCredentialUseCase.Execute`; последний вызывается фоновым обходом.

Профиль запускает проект в окружении `Development`, через HTTP, без IIS,
Docker, HTTPS-сертификатов и автоматического открытия браузера. Адрес
`http://localhost:5080` задаётся единственной настройкой `Urls` в
`appsettings.json`. Маршрута `/` нет: для запросов используйте `.http`-файл.
Если порт занят, освободите его или поменяйте `Urls` и `baseUrl` в `.http`.

БД создаётся автоматически в `src/CredentialAuthority.Api/data/credentials.db`.
Локальные `.idea`, настройки пользователя, результаты сборки и БД исключены
из Git. В общих файлах нет абсолютных путей и настроек конкретного компьютера.
`.http` генерирует нового владельца и будущую дату при каждом создании,
поэтому пример не зависит от ранее выданных удостоверений и календарной даты.

## Запуск и проверка

Нужен стабильный .NET SDK 10.0.100 или более новый SDK 10.0.
`global.json` разрешает более новые feature band версии 10.0; точная
версия SDK автора приложения не требуется.
Первый restore требует доступа к nuget.org. Дальнейшая работа приложения
не требует внешних сервисов.

Из корня репозитория:

```shell
cd src
dotnet restore CredentialAuthority.sln
dotnet build CredentialAuthority.sln --no-restore
dotnet test CredentialAuthority.sln --no-build
dotnet run --project CredentialAuthority.Api --no-build --launch-profile CredentialAuthority.Api
```

API доступно на `http://localhost:5080`. Файл БД по умолчанию:
`src/CredentialAuthority.Api/data/credentials.db`; схема и каталог создаются
одноразовым воркером при запуске. HTTP-сервер и обработчик выдачи запускаются
после успешной инициализации; ошибка инициализации прерывает запуск.
Настройка `Database:Path` задаёт путь относительно каталога
API-проекта или абсолютный путь. Например, из `src`:

```shell
Database__Path=/tmp/code-review-task-demo.db dotnet run --project CredentialAuthority.Api --no-build
```

`Issuer:Name` задаёт имя единственного издателя; изменение настройки влияет
на новые заявки, уже принятые сохраняют своего издателя.

Пример полного сценария (выберите будущую дату и ещё не занятого владельца):

```shell
curl -i http://localhost:5080/requests \
  -H 'Content-Type: application/json' \
  -d '{"ownerName":"Ivan.Petrov","validUntil":"2030-12-31T23:59:59Z"}'
```

Скопируйте ID из ответа `202` и подставьте его вместо `ID`:

```shell
curl -s http://localhost:5080/requests/ID
```

Повторите GET после ближайшего 10-секундного обхода. При `Issued`
возьмите `credentialUrl` из карточки и запросите документ по этому пути,
например:

```shell
curl -s http://localhost:5080/credentials/SERIAL_NUMBER
```

Ошибки имени/срока дают `400`; повторный POST для занятого владельца —
`409`. Чтобы увидеть `Rejected`, задайте срок, который наступит до следующего
обхода; после отказа разрешена новая заявка с будущим сроком.
